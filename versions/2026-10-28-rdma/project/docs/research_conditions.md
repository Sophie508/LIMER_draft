# 本轮 condition 的来源与精确定义

这些是我们预先设计的仿真注入条件，不是从真实机房日志抽样得到的故障。
健康、25% 容量、0.5% 丢包和黑洞沿用合作者的故障类型；80 ms 延迟和额外
边界用于检验本轮检测与换路判断。参数不是某篇论文规定的统一 benchmark。
最终依据是冻结的 `registration.json` 与每个 `cases/*.json`，而不是表格简称。

| Condition | 实际注入 | 用来回答什么 |
| --- | --- | --- |
| `healthy` | 无故障注入，仍运行探测至观察上限 | 是否误报；同轨迹重复不增加业务覆盖 |
| `blackhole` | 一个 GPU 的 B 接入链路双向丢包率 100% | 完全无法交付时，检测与抢救能否完成 |
| `quarter` | 同一 B 接入链路双向 service fraction=0.25，丢包率 0 | 链路仍能传输，是否检测持续降速 |
| `weak_loss` | 同一 B 接入链路双向独立逐包丢包率 0.005，service fraction=1 | 传输能修复的少量丢包是否仍形成及时告警 |
| `delay` | 同一 B access channel 的单向传播时延设为 80,000,000 ns，无人工丢包或降速 | 严重变慢也属于交付异常，不必证明永久丢失 |
| `transient_2ms` | 双向黑洞只持续 2 ms，随后恢复 | 对短故障和残留业务停滞，是否还值得切换 |
| `slow_proxy_1gbps` | 黑洞，同时本地代理链路设为 1 Gb/s | 慢代理在必须恢复时的代价 |
| `no_idle_helpers` | server 0 的四个 GPU（0–3）B 接入链路同时黑洞 | 能定位并不代表存在可用代理 |
| `slow_proxy_quarter` | B service fraction=0.25，同时本地代理链路 1 Gb/s；专用长 phase 负载 | 直接 B 仍能服务时，健康但昂贵的代理是否反而拖慢 |

注入代码在 `python/limerlab/inputs.py::inject` 和
`src/simulator/experiment/faults.h`。注入真值只供事后评分；检测和收益判断
不读这些文件、service fraction、丢包率、故障位置或未来恢复时间。

## 所有方法共享的模型

16 个 GPU、每服务器 4 个 GPU，物理 A/B 双平面，接入速率 10 Gb/s。
本地代理链路的常规模型参数为 2400 Gb/s；1 Gb/s 是人为设置的慢代理边界，
不代表真实硬件配置。每个原路径每 2 ms 一个 64 KiB canary，前 20 ms
做校准。所有方法都支付同一检测成本，两种 G11 还支付同样的三段候选探测。

常规负载是 2 个 ring rounds，共 60 个 phase；每个 rank 每 phase 64 个
64 KiB chunk，总逻辑交付 4,026,531,840 B（约 4.03 GB）。观察至 400 ms，
业务起点为 1 ms，所以未完成任务的截尾成本为 399 ms。
慢代理 + quarter 单独采用 1 round、30 phase、256 chunks，总逻辑交付
8,053,063,680 B（约 8.05 GB），观察至 800 ms，截尾成本 799 ms。

原截图采用不同 phase 粒度，不能把本轮均值直接除以截图数字当作跨版本加速比。
本轮性能结论来自相同输入、同样上限的三方法配对。

## 采样与验收

四类持续主故障各 60 个新 seed。节点在 16 个 GPU 中均匀抽取，故障时间在
35–55 ms 中均匀抽取；同 trial 的三方法共享输入。无空闲代理条件固定故障节点
0–3，随机节点字段不改变这个继承的多故障定义。新验证 seed base 为
102990000，与第一轮全部 seed 不重叠。

另一个独立性问题单独处理：旧注入器实际用 `seed+node` 派生丢包随机流，
主矩阵的 60 次弱丢包只对应 38 个不同的随机流对。原结果保留，但不能把
它的名义二项式下界当成独立抽样保证。补充队列另预注册 60 次弱丢包，
base=103100000、stride=32，保持二进制、规则参数和负载一致。最终弱丢包
检测行只使用这 60 次新队列，不与旧 60 次合并；策略配对仍来自主矩阵。

一次及时成功要求所有受影响方向都严格小于 100 ms，且全观察窗口没有
提前报警或误定位。漏检、迟报、错误和未跑案例保留在各行分母。通常一个
access 故障影响两条有向原路径，无代理场景影响八条；只报最早一条不能替代。

## 接收间隔信号的依据

包间隔作为端到端测量信号有经典研究基础，也会受到交叉流量与包长等因素
影响：[Dovrolis, Ramanathan and Moore, ToN 2004](https://ieeexplore.ieee.org/document/1369287/)。
本轮 P10 变化检测是我们针对当前模型的实现选择，不是该论文证明的通用规则，
也没有复现 Pathrate。开发中单独 canary 的间隔受 QP 轮询混杂，故改为同路径
所有完整业务/探测包的接收间隔，并由原始 packet trace 独立重放。

本仿真接收事件提供理想的纳秒时间戳，尚未加入软件时间戳噪声。真实用户态
测量还会受主机调度干扰，见作者的 [Pathrate 使用说明](https://faculty.cc.gatech.edu/~dovrolis/bw-est/pathrate_tutorial.html)。
当前工作按用户要求只验收 simulation，不把该测量精度当成硬件实测事实。
