LIMER — fault detection architecture

Two failure modes.
Two detection paths.

How a hard link failure and a gray (rate-capped, still-UP) failure get found in our active–active testbed — and why hitting sub-millisecond detection meant changing the mechanism, not tuning the old one.

01 — framing

Two things we both call “a fault”

Same physical topology, same injected impairment on worker 2's link to Fabric A — but the evidence each one leaves behind is completely different.

Hard failure

The link goes down.

Physically or administratively severed. Carrier is lost on both ends. The kernel already knows the instant it happens — this is exactly the state it was built to track.

Nothing to infer. Just a state to read.

Gray failure

The link stays up — but starved.

Operationally and administratively UP the entire time. The interface reports itself healthy. Only the traffic actually moving across it carries the symptom.

Nothing to read. Everything to infer.

→ This split is the whole story. One failure mode hands you a signal for free; the other gives you none. Everything downstream — how we inject each one, how we detect each one — follows from that one fact.

02 — how we build the fault (Q2)

Manufacturing both faults in the testbed

Four workers, two fabrics (A/B), Mininet + Open vSwitch. Both faults target the same link — worker 2's egress to Fabric A — with two different Linux primitives.

Both commands run inside the worker's network namespace, on the same physical edge.w2-eth0 → Fabric A
The gray injector is Linux tc/netem — a queueing discipline that rate-limits egress without touching link state. That's not an implementation detail: it's the entire reason gray detection needs a second mechanism. The interface's own status line has nothing wrong to report.

03 — the key difference (Q3)

Why one mechanism can't cover both

Detection isn't one faster loop wrapped around both faults. It's two independent mechanisms, chosen by what evidence actually exists.

This is the key difference, in one sentence: hard-failure detection reads a fact that already exists in the kernel; gray-failure detection has to manufacture a fact by watching traffic over time. One is a lookup. The other is a measurement.

04 — deep dive (Q1)

Hard-fault detection: from checking to being told

The old architecture had no dedicated path for a hard failure at all — it just eventually looked like an extreme case of the same gray-fault symptom. The fix wasn't a faster poll. It was removing the poll.

05 — deep dive (Q1)

Gray-fault detection: the baseline was measuring the wrong thing

Healthy egress traffic isn't a steady stream — it's bursty: full-rate transmission windows separated by near-idle gaps between sends. The old rule blended both into one number.

what changed
baseline scope
calibrate only on burst-mode windows, not the blended average
measured (3 repeats)
51.8–53.3 ms
target: < 100 ms
judgment
statistical
2 consecutive bursts < 60% of the burst-mode baseline
